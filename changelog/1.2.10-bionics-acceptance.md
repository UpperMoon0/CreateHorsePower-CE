## Acceptance workflow and scope

`.github/workflows/bionics-compatibility.yml` is called by the main `CI` workflow. The opt-in Gradle flag is `-PbionicsCompatibilityTest=true`, with isolated namespace `createhorsepower_bionics`. Both builds without Bionics are checked by the normal pipeline.

Real-mod GameTests require the matching mod version and entity registry. They exercise incomplete assembly, finite/creative fuel, taming policy, rider/water exclusion, invalid paths, redstone shutdown, detach/reattach, measured two-lap orbit and generated power/fuel consumption. NeoForge additionally tests its actual Bionics plough/harvester part entities on the **server** for survival/creative lead interactions; it does **not** simulate a graphical client raycast or all real player network packets.

The restart runner invokes two **separate JVMs** against the **same isolated world**. The probe requires `createhorsepower.bionicsExpected=true` in each `runServer` process and validates persisted assembly, fuel, entity/crank UUID, displacement and RPM. Missing dependencies, missing scenarios, absent evidence, failing writes and skipped tests fail the workflow.

## Additional Forge dedicated-server compatibility defect

The unmodified pinned Forge upstream Bionics source calls `SoundScapes.play()` (a client-only Create helper) through `OxhaulerEntity.tick()` on **the logical server**, and Create/Catnip attempts to read the uninitialized client config. The required Forge GameTest run `40942481706` crashed with `Cannot get config value before config is loaded` while ticking the real Bionics robot. CE now uses an optional bytecode-validated mixin against the upstream `playSoundScape` method: on logical servers it cancels **only ambient audio**, while the real robot entity still ticks and drives the crank. Client audio and NeoForge's existing logical-side guard remain unaffected. This is an explicit compatibility shim, not proof that upstream Forge Bionics is safe independently of CE.
